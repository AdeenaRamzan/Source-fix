# SourceFix demo cases

All three cases below were generated by running `generate_demo_cases.py`
against the real FastAPI app (`app/main.py`) and the bundled synthetic
dataset (`app/data/suppliers.json` + `app/data/product_brief.json`), pinned
to `reference_date = 2026-08-08` for reproducibility. Each `.json` file
contains the exact request body and response body for every API call made,
so they can be dropped straight into the submission or screenshotted as-is.

**A note on the LLM calls in cases 1 and 3:** this sandbox has no live
`GROQ_API_KEY` configured, so `propose_relaxation_node` and
`rank_and_finalize_node` were run with deterministic stand-in functions
representing plausible real model output for the given prompt (documented
inline in `generate_demo_cases.py`, the same dependency-injection seam
`tests/test_agent.py` already uses). The graph wiring, `apply_relaxation_node`'s
guardrails, `eligibility_filter`, and the FastAPI layer are all real,
unmodified code — nothing about the *decision logic* is faked, only the raw
model text going in. Case 2 never touches an LLM at all. Swap in a real key
and delete the two monkeypatches in the script to reproduce cases 1 and 3
against a live model.

## Case 1 — Successful: `case1_successful_relaxation.json`

This case demonstrates the system's core value proposition end to end.
Step A calls `/api/baseline` with the full, unrelaxed constraint set and
confirms zero suppliers are eligible — the same zero-eligible result the
non-agent baseline is designed to produce, since every supplier is exactly
one soft requirement short of a clean pass (SUP-001 and SUP-013 both fail
only on `sustainability_score`, at 55 and 59 against a 60 floor). Step B
runs the full agent (`/api/analyze`) against the identical data: it
identifies `sustainability_score` as the soft constraint with the most
current failures, proposes lowering the floor to 50, and
`apply_relaxation_node` accepts it in exactly one iteration because the
field is genuinely marked `soft` in `working_constraints`. The re-run filter
then finds two eligible suppliers, and `rank_and_finalize_node` produces a
ranked shortlist whose explanations cite only values actually present in
the filter's own data (certification status, capacity, quality score, MOQ,
lead time, region, and the now-passing sustainability score for each
supplier) — nothing about pricing, reputation, or any other unsupported
claim. The relaxation ledger, `working_constraints` diff, and final
`message` ("Shortlisted 2 supplier(s) after 1 relaxation attempt.") give a
full, auditable trail from "nobody qualifies" to "here are two ranked,
data-grounded picks."

## Case 2 — Ambiguous: `case2_ambiguous_certification.json`

This case demonstrates that conflicting source data is never silently
dropped or silently accepted — it is flagged, explained, and excluded.
SUP-008 (Meridian Tooling Ltd.) has a certification record where
`status = "expired"` but `expiry_date = 2027-01-01`, which is still in the
future relative to the pinned reference date — the two fields disagree
about whether the certificate is valid. `check_constraint()` in
`tools.py` detects exactly this disagreement and fails the supplier
closed, with a reason string that states the conflict explicitly:
*"AMBIGUOUS certification record — status field says 'expired' but
expiry_date 2027-01-01 is still in the future as of 2026-08-08. Conflicting
source data; does not count as a valid certification until verified."*
SUP-008 is confirmed absent from `eligible` in the baseline response, and
because `certification` is a hard, non-negotiable requirement, no amount of
soft-constraint relaxation in a full agent run could ever change that — the
only path to including SUP-008 is a human resolving the conflicting source
record, which is exactly the outcome this design intends. The supporting
`cite_lookup()` calls attach the exact raw field values (`source_row: 8`) an
auditor would need to go verify the record themselves.

## Case 3 — Failure / fallback: `case3_failure_manual_review.json`

This case demonstrates that the system reports a clean, final "give up"
rather than guessing at a shortlist or looping forever, and — just as
importantly — that this can happen even when every individual relaxation
*proposal* is reasonable and gets accepted. The supplier pool was
constructed from the seven suppliers in the dataset that each fail at least
one **hard** requirement (certification, minimum capacity, or minimum
quality history score) — SUP-005, 006, 007, 008, 010, 011, 012. Across 3
iterations the agent proposes three ordinary, good-faith soft relaxations
(`sustainability_score`, then `moq_units`, then `lead_time_days`), and
`apply_relaxation_node` legitimately accepts all three — they are valid
soft fields, correctly shaped. None of them can ever produce an eligible
supplier, though, because the real blocker for every candidate is a hard
requirement, and hard requirements are never relaxed by design. Once
`iteration` reaches `max_iterations = 3` with `eligible` still empty,
`decide_next` routes to `give_up_node`, which sets
`status = "no_shortlist_found"`, `final_shortlist = []`, and — per the
brief's required wording — `message = "No defensible shortlist found after
3 relaxation attempts -- manual review needed."` `rank_and_finalize_node`
is never invoked (asserted in the script), so no ranking or explanation is
ever fabricated for a shortlist that doesn't exist.
